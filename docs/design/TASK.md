## Layer 2：身分與帳號

**UC 範圍**：MVP1：UC-ACT 3.2.1、3.3.1、3.4.1.1、3.5.5、4.3.3；MVP2：4.3.1、4.3.2（SSO）

**目標**：email 為帳號；**MVP1 登入流程（2026-10-24 使用者決定）：輸入邀請碼與 email → 驗證後寄 token 到信箱 → 以 token 登入**；首次註冊需邀請碼與顯示名稱。Google / Microsoft SSO（UC 4.3.1、4.3.2）暫移 MVP2，同 email 跨方式視為同一帳號的規則於加入 SSO 時驗收。**已確認的規則（使用者 2026-10-24）**：token 一次性、10 分鐘有效；僅**第一次**需要邀請碼，之後只輸入 email；寄信採 outbox 模式（訊息先寫入資料表，job 每 1 分鐘撈未發送者呼叫發信 API，成功才更新 flag），SMTP 暫不處理。**token 為連結（使用者 2026-10-24）**，點擊連結即登入（P1a 驗證頁）；發信 job 與發信 API 待使用者之後提供細節。

**設計建議（待使用者確認，見 ADR-003 草稿）**：(1) token 以雜湊儲存，不存明文；(2) outbox 內文含 token，寄出後應清除或遮罩內文；(3) flag 建議用 pending / sent / failed 加重試次數，而非單一布林；(4) 撈取用 `FOR UPDATE SKIP LOCKED` 避免多副本重複寄；(5) 每分鐘輪詢代表登入信最長延遲約 1 分鐘（token 有效期 10 分鐘仍夠用），若實測體驗差再縮短輪詢；(6) 新 token 產生時，舊 token 作廢。

**驗收條件**：
| UC 編號 | 功能 | 成功路徑 | 失敗路徑 |
| ------- | ---- | -------- | -------- |
| UC-ACT 3.3.1.1 | email token 登入 | **已註冊 email**：只輸入 email → 產生 token 並寫入寄信 outbox → 收信後以 token 登入；**未註冊 email**：要求邀請碼 + 顯示名稱後註冊 | token 過期（10 分鐘）/ 已使用（一次性）/ 已被新 token 取代 → 繁中說明不登入；邀請碼無效 → 不建帳號；對未註冊與已註冊 email 的回應訊息一致（不洩漏帳號是否存在）；連續請求過頻 → 限流 |
| UC-ACT 3.3.1.2 | 邀請碼註冊 | 有效邀請碼 + 顯示名稱 → 建立帳號並歸屬預設組織 | 邀請碼無效 / 已用 / 過期 → 拒絕，不建立帳號 |
| UC-ACT 3.3.1.3 | Session 與帳號合併 | 先 magic link 後 Google，登入同一帳號、學習紀錄不分散 | 未登入呼叫受保護 API → 401；Session 過期 → 401 |

| UC-ACT 3.2.1 | P1 登入頁 | 三種登入方式可走完 | 全部錯誤路徑畫面無英文句子 |
