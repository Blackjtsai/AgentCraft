# MVP1 範圍與時程（含前台與後台畫面）

> 版本：v0.2 ／ 2026-10-24 ／ 狀態：範圍已由使用者確認，時程待使用者另行安排
> 決定依據（使用者 2026-10-24）：
> - **POC 上有的功能 MVP1 都要全做**（含情境製作 Studio）。
> - **先不管人力**，專案時程由使用者之後安排。
> - **MVP1 要有前台與後台畫面**；至少 50 人同時使用；**300 人試用放在雲端**。
> - **本機開發完畢後，最後一個星期才做打包部署與雲端測試。**
> - 後台**只有一個 `admin` 管理員**；開發期密碼先固定（見 §3 安全提醒）。
> - MVP2 內容未知，先不規劃。
> 基礎架構：web、api、job、backend、redis、postgresql、nas。團隊目前 PM/SA 1 人 + SD/PG 1 人。

## 1. MVP1 目標

| 項目 | 內容 |
| ---- | ---- |
| 時間 | 2026/11 底（時程由使用者另行安排） |
| 規模 | 300 人試用（**雲端**）；**至少 50 人同時使用**，每人對話互不影響（OV-03） |

## 3. 關鍵規則（已定）

- 學員登入：連結一次性、10 分鐘；首次需邀請碼，之後只輸入 email；寄信走 outbox 資料表，job 每分鐘撈未發送者呼叫發信 API，成功後更新 flag。
- 後台登入：**單一 `admin` 帳號**，帳密登入。
- LLM 使用 Gemini API（是否經 AI Gateway 待確認）；模擬系統由 Orbit 的 Digital Twin 提供。
- 情境可由後台動態新增，存資料庫並有版本；已開始的練習停留在原版本。
- 完成判定看模擬系統的實際結果，不看 Agent 說了什麼。
- 所有錯誤訊息繁體中文，不顯示英文技術字串。
- 開發順序：**本機開發 → 最後一個星期打包部署與雲端測試**。

### 安全提醒（請看）

**admin 密碼開發期固定（簡單值，實際值不寫進文件或 git），只能是「本機開發期」的做法**。因為 300 人試用放在雲端，後台一旦上線，簡單的固定密碼等於沒有保護：任何知道網址的人都能新增 / 下線情境、停用帳號、看使用紀錄。我建議：
1. 密碼**不寫死在程式或 git**，改由環境變數提供（例如 `ACT_ADMIN_PASSWORD`），開發值只放在不進版控的 `.env`；`.env.example` 只放空值或佔位字，且未設定時服務應拒絕啟動，不回退到預設密碼。
2. **雲端部署前一定要換成強密碼**，並列為部署週的檢查項目（見 TODO）。
3. 後台限制來源（例如只開放辦公室網段）、登入失敗限流與鎖定。
4. 密碼以雜湊比對，不以明文比對。

## 4. 工時（人工開發基準；未計 AI 輔助；**僅供排程參考，不做人力限制**）

| Layer | 內容 | 人天 |
| ----- | ---- | ---- |
| 1 | 基礎建設與資料層（不含打包部署） | 6.5 |
| 2 | 身分與帳號（email 連結登入、邀請碼、郵件 outbox job） | 9 |
| 3 | 情境包、動態管理 API、素材、Digital Twin 串接 | 21 |
| 4 | Agent、完成判定、學習紀錄、換案測試 | 21.5 |
| 5 | 學員前台 P2–P7、教學、導覽 | 16 |
| 6 | 安全、營運、用量，＋後台 A0–A4 畫面 | 15 |
| 7 | **Scenario Studio（已改列 MVP1）** | 12 |
| 8 | 端對端、50 人同時壓測、**最後一週：打包部署與雲端測試** | 11.5 |
| | **合計** | **約 113** |

> 2 人實際開發力約 35–40 人天，與 113 的落差很大；使用者表示「先不管人力、時程另行安排」，此處僅記錄事實。Layer 3、4 還取決於 Orbit 介面與 Agent 執行位置，等待時間不在上表。Layer 7 的細節在開始前再估。
