## 體驗觀察（驗證時要比對的行為）

**流程與資訊結構**
- 第二關頁籤在第一關完成前顯示「第二關・完成第一關後開放」且不可點 → 對應 SITEMAP「P6 完成第一關前不可進入」。
- 系統卡片依 Agent 實際使用亮起並顯示「資料已查回 · N 次」；點開檢視**不會觸發查詢或操作**。
- 提醒文案：「操作『已受理』不等於成功，查回結果才確認」。完成判定看實際結果。
- 登入後首頁即為「我的學習」；探索新情境在其下方。

**方案確認機制（P5 核心）**
- Agent 先查（本次共 17 筆查詢，含 HIS、規則庫、聯絡紀錄、排班），再出**方案卡**，學員按「同意 / 不同意 / 修改」才會聯絡病患。
- 方案卡列出每位病患的「將執行動作」與「可提供選項」（具體場次），並寫明執行條件與停止條件。
- 同意後 Agent 只在該方案範圍內執行，超出範圍會再請學員確認。
- 方案確認前輸入框提示「可以先問 Agent 問題，方案會保留」。

**效能與可靠性（重要，影響回應時間目標與 Layer 4 / 6）**
- 起始 Prompt 送出後，Agent 數分鐘仍在「處理中」（擷取時 5 → 13 → 17 筆查詢），**實測出方案花了超過 10 分鐘**（輪詢間隔粗略，非精確量測；中途我重新載入頁面數次，是否影響執行未確認）。
- 作為對照，PRD 把「回應時間目標」列為**未決**；此體驗顯示目標必須定義，且「串流顯示執行步驟」對可用性很關鍵。
- 每日用量以「次」計：送出一則訊息計 1 次（「今天已用 1 / 100 次」）。
- Studio 的 LLM 呼叫失敗時直接顯示 `ModelHTTPError`（英文技術錯誤外洩，違反 PRD OV-01）。畫面有「可以再試一次」的補救。

**響應式**
- 手機與平板（390、820 寬）實測**無整頁橫向捲動**；手機工作台改頁籤。

**LLM 額度與錯誤處理（2026-10-24 體驗到，對我方設計很重要）**
- 走第一關途中，POC 的 Agent 失敗並顯示：模型服務出錯，附上 `status_code: 429`、模型名稱 `gemini-3.8-flash`、**完整的英文錯誤內容**（含配額代碼、重試秒數、供應商網址）。畫面截圖：`36-p5-after-run2.png`。
- 原因：POC 使用 Gemini **免費方案**，每個模型**每日上限 20 次請求**，已用完，約 23 小時後恢復。**沒有付費額度或備援模型時，POC 一天只能跑極少量對話。**
- 對我方的意義：
  1. **LLM 額度是 MVP1 的硬限制**：50 人同時、300 人試用，一輪 Agent 對話就會呼叫 LLM 多次（本次單一案件 31 筆查詢與操作），必須使用付費額度並有用量與限流設計（接 TODO 的 Gemini API 資料）。
  2. 429 要有**繁中友善訊息**與自動排隊 / 重試策略；POC 直接外洩英文錯誤與內部配額資訊，違反 OV-01，也不應向學員揭露供應商細節。
  3. 「每人每日 100 次」的應用層限額，擋不住供應商端的額度，兩層要分開設計。
- POC 保存了進度（「已執行的步驟都已保存」），額度恢復後輸入「繼續」可接著做。

**第一關後半段實際流程（已觀察到）**
- 同意方案 → Agent 打電話（模擬病患回覆）：病患聯絡平台「完成 11、暫停 1」→ 出現**情境事件**暫停 → 學員回覆後 Agent 更新方案（方案 2：王○明改選 A 醫師下週場次，另兩位維持）→ 再次同意 → 繼續執行，並已建立 1 筆交接（轉交人員紀錄）。
- 方案 2 的畫面見 `33-p5-plan-before-approve.png`；情境事件畫面見 `30-p5-after-run1.png`（`34` 實為 429 錯誤畫面）。
