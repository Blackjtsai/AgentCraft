# ADR-003：MVP1 登入 token 與郵件 outbox

> 狀態：草稿（規則已由使用者決定，實作細節待確認）
> 日期：2026-10-24
> 決策者：BlackJ-Tsai

## 背景

PRD 規劃 magic link、Google SSO、Microsoft SSO 三種登入。MVP1 團隊只有 2 人、11 月底 300 人，需縮範圍。使用者決定第一階段只做「email token 登入」，SSO 後移。

## 已決定的規則（使用者 2026-10-24）

- token **一次性**、**10 分鐘**有效。
- **第一次**需輸入邀請碼（與顯示名稱）；之後只輸入 email 即可登入。
- 寄信採 **outbox 模式**：產生 token 時，把訊息寫入資料表；**job 每 1 分鐘**撈出尚未發送的資料，呼叫發信 API，**成功才更新 flag**。
- SMTP 暫不處理。
- token 形式為**連結**（點擊即登入）；發信 job 與發信 API 細節由使用者之後提供。

## 選項（寄信方式）

| 選項 | 優點 | 缺點 |
| ---- | ---- | ---- |
| A 同步呼叫發信 API | 即時 | 發信失敗直接影響登入請求；重試與併發難處理 |
| **B outbox + job（採用）** | 登入請求與外部服務解耦；失敗可重試；可稽核 | 信件最長延遲約 1 分鐘；需處理併發與重試 |

## 決策

採用 B。以下為**建議，待使用者確認**：

1. token 以雜湊儲存，不存明文；新 token 產生時舊 token 作廢。
2. outbox 內文含 token，**寄出成功後清除或遮罩內文**，避免密鑰長期留在資料表。
3. flag 用 `pending / sent / failed` 加重試次數，不用單一布林，才能區分「還沒寄」與「寄不出去」。
4. job 撈取使用 `FOR UPDATE SKIP LOCKED`，避免多副本重複寄送。
5. 對未註冊與已註冊 email 回應一致，避免洩漏帳號是否存在；對 email 與 IP 限流。
6. 每分鐘輪詢使登入信最長延遲約 1 分鐘（token 有效 10 分鐘仍夠用）；若實測體驗不佳，縮短輪詢間隔即可，不影響架構。

後果：登入依賴 job 存活，`/checkservice` 與告警要涵蓋 job；outbox 表屬於「不可變紀錄」以外的可更新表，需 `update_*` 欄。
